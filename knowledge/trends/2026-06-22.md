## 2. 前回（2026-06-15）からの差分：新規確認事項

### 2-1. スキル（Skills）がベストプラクティスの中核機能として格上げ

前回調査では CLAUDE.md・サブエージェント・フックが中心だったが、今回の公式 best-practices ではスキルが独立した推奨機能として明記された。

**SKILL.md の公式フォーマット（ベストプラクティスより）:**
```markdown
# .claude/skills/api-conventions/SKILL.md
---
name: api-conventions
description: REST API design conventions for our services
---
# API Conventions
- Use kebab-case for URL paths
- Use camelCase for JSON properties
```

**`disable-model-invocation: true` の用途明文化:**
```markdown
---
name: fix-issue
description: Fix a GitHub issue
disable-model-invocation: true
---
```
副作用のあるワークフロー（コミット・PR作成等）は `disable-model-invocation: true` を設定して手動トリガー専用にする。

**スキル vs CLAUDE.md の公式使い分け原則:**
- CLAUDE.md: 毎セッション必要な情報（コンベンション・ビルドコマンド）
- スキル: タスク固有・繰り返しのワークフロー・参照ドキュメント → **オンデマンドロード**でコンテキスト節約

### 2-2. プラグイン（Plugins）の位置づけ明確化

**プラグイン = スキル + フック + サブエージェント + MCP サーバーのバンドル**

```bash
/plugin  # マーケットプレイスを開く
```

**コードインテリジェンスプラグイン**が特に推奨:
- TypeScript・Python等の型付き言語向け
- シンボルナビゲーション・自動エラー検出を提供
- インストールするだけで設定不要

### 2-3. フック（Hooks）5タイプの完全ドキュメント確認

前回まで主に `command` タイプが中心だったが、今回すべての5タイプが詳細確認できた:

| タイプ | 概要 |
|--------|------|
| `command` | シェルスクリプト（stdin で JSON 受信）|
| `http` | 外部エンドポイントへの POST |
| `mcp_tool` | MCP サーバーのツールを直接呼び出し |
| `prompt` | LLM に yes/no 判断を委ねる |
| `agent` | 検証用サブエージェントをスポーン（実験的） |

**フックプレースホルダー変数（新規確認）:**

| 変数 | 内容 |
|------|------|
| `${CLAUDE_PROJECT_DIR}` | プロジェクトルート |
| `${CLAUDE_PLUGIN_ROOT}` | プラグインのインストールディレクトリ |
| `${CLAUDE_PLUGIN_DATA}` | プラグインの永続データディレクトリ |

**exec 形式（`args` フィールドあり）vs シェル形式（`args` なし）の使い分け（明文化）:**
```json
// exec形式（シェルを介さず安全）
{
  "command": "node",
  "args": ["${CLAUDE_PLUGIN_ROOT}/script.js", "--fix"]
}

// シェル形式（パイプ・&&が使える）
{
  "command": "node \"${CLAUDE_PLUGIN_ROOT}\"/script.js --fix"
}
```

**フック設定場所の全一覧（明文化）:**

| 場所 | スコープ | 共有可否 |
|------|----------|---------|
| `~/.claude/settings.json` | 全プロジェクト | 不可（個人） |
| `.claude/settings.json` | 単一プロジェクト | 可（VC管理） |
| `.claude/settings.local.json` | 単一プロジェクト | 不可（個人） |
| プラグイン `hooks/hooks.json` | 有効時のみ | 可 |
| スキル/エージェントのフロントマター | アクティブ時のみ | 可 |
| Managed policy settings | 組織全体 | 強制 |

**JSON 出力フォーマットの詳細（新規確認）:**
```json
{
  "continue": true,
  "suppressOutput": false,
  "systemMessage": "警告メッセージ",
  "terminalSequence": "エスケープシーケンス",
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "理由"
  }
}
```

`additionalContext` でシステムリマインダーをコンテキストに注入:
```json
{
  "hookSpecificOutput": {
    "hookEventName": "PostToolUse",
    "additionalContext": "このファイルは生成済み。src/schema.ts を編集すること"
  }
}
```

**`/hooks` メニューの詳細（新規確認）:**
- 設定済みフックをイベント数・マッチャー・ソース（User/Project/Local/Plugin/Session/Built-in）付きで一覧表示
- 読み取り専用（設定編集は直接 JSON ファイル）

**組織管理者向けフック制限:**
- `allowManagedHooksOnly: true` でユーザー/プロジェクトフックをブロック
- Force-enabled プラグインはこの制限から除外

### 2-4. Auto Mode の非インタラクティブ時の動作仕様（新規確認）

```bash
claude --permission-mode auto -p "fix all lint errors"
```

**新規判明:** `-p` フラグとの組み合わせ時、分類モデルが繰り返しブロックすると**自動的に中断（abort）**する。インタラクティブモードではフォールバックできるが、非インタラクティブでは継続不可のため。

> "For non-interactive runs with the `-p` flag, auto mode aborts if the classifier repeatedly blocks actions, since there is no user to fall back to."

### 2-5. `/goal` 条件の詳細仕様（明文化）

前回は存在のみ確認だったが、今回の公式文書で詳細仕様が確認できた:

> "/goal condition: A separate evaluator re-checks it after every turn and Claude keeps working until it holds."

- **別の評価エージェント**が毎ターン後に `/goal` 条件をチェック
- 条件を満たすまで Claude が作業継続
- Stop フックとの違い: Stop フックは決定論的（スクリプト）、/goal は LLM による評価

**品質ゲート 4段階の整理（更新）:**

| レイヤー | 方法 | セットアップコスト | 自律度 |
|---------|------|-----------------|--------|
| 1 | プロンプト内の検証指示 | 低 | 手動 |
| 2 | `/goal` 条件（評価エージェントが毎ターン再チェック） | 中 | 高 |
| 3 | Stop フック（スクリプトゲート、最大8回ブロック） | 中 | 最高 |
| 4 | 検証サブエージェント（独立コンテキストで批評） | 高 | 高 |

### 2-6. `/rewind` の「要約」2モードの区別（新規確認）

公式ドキュメントで `/rewind` の2つの要約モードが明文化された:

- **"Summarize from here"**: 選択したメッセージ以降を要約（それより前のコンテキストは完全保持）
- **"Summarize up to here"**: 選択したメッセージより前を要約（最近のメッセージは完全保持）

セッション間でもチェックポイントは保持される:
> "Checkpoints persist across sessions, so you can close your terminal and still rewind later."

### 2-7. インタラクティブ `/init` フロー（`CLAUDE_CODE_NEW_INIT=1`）の詳細確認

前回から記録はあったが、今回の公式ドキュメントで多段階フローが詳細確認できた:

1. セットアップするアーティファクトを選択（CLAUDE.md / スキル / フック）
2. **サブエージェント**でコードベースを探索
3. フォローアップ質問で空白を埋める
4. **レビュー可能な提案を提示**してから書き込み

既存 CLAUDE.md がある場合は上書きせず改善提案を行う。

### 2-8. Auto Memory の動作詳細（確認・補足）

**MEMORY.md の読み込み制限（明確化）:**
- 先頭 **200行 または 25KB** のいずれか早い方をセッション開始時にロード
- トピックファイル（`debugging.md` 等）はオンデマンドロード（起動時は非ロード）
- MEMORY.md はコンテキスト節約のため簡潔なインデックスとして保つ

**サブエージェントの Auto Memory:**
- サブエージェントも独自の Auto Memory を持てる（`memory: user` で `~/.claude/agent-memory/` に保存）
- 詳細は `sub-agents.md#enable-persistent-memory` 参照

### 2-9. CLAUDE.md の `claudeMd` マネージド設定キー（確認・補足）

```json
{
  "claudeMd": "Always run `make lint` before committing.\nNever push directly to main."
}
```

- `managed-settings.json` の `claudeMd` キーで CLAUDE.md コンテンツを直接埋め込み可能
- 専用ファイルを展開せず、MDM/Ansible 等の設定ファイルで一元管理できる

### 2-10. サブエージェント設計の明文化（新規確認）

公式 sub-agents.md での利用目的の明文化:
1. **コンテキスト保護**: 調査・実装の副作用をメイン会話から隔離
2. **制約の強制**: 許可ツールをサブエージェント単位で制限
3. **設定の再利用**: ユーザーレベル定義で全プロジェクト横断
4. **専門特化**: フォーカスされたシステムプロンプトで特定ドメインに特化
5. **コスト制御**: Haiku 等の安価なモデルにルーティング

**コンテキストウィンドウ可視化リソース（参照先）:**
公式ドキュメントが「コンテキストウィンドウ可視化ページ」（`/en/context-window`）を複数箇所で参照。サブエージェントがいかにコンテキストを節約するかをインタラクティブに確認できる。
